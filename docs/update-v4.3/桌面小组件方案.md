# Karma 每日必做桌面小组件方案

> 已获用户批准并实施完毕（提交 `v4.3-改14` ~ `v4.3-改22`）。
> 版本沿用 v4.3（v4.3 的改1~改13 为原有内容）。
>
> **落地过程中用户纠正过一次行为**：最初实现为「点圆圈一律打开 App」（为了弹自证），
> 用户明确不接受，改为「**点击直接写库、不打开 App；只有加分跨入更高正阶位时才打开 App 弹自证**」。
> 下文为**最终定稿**方案。

---

## 一、需求

> 用户原话：
> 「我的手机是华为 mate50，不是满血鸿蒙系统，因此能使用这个软件。现在我要让手机桌面上多出一个小组件（服务卡片），2*2 大小，里面显示没有完成的每日必做，每一行前面会有一个圆圈，如果我点击了圆圈，这一行事件就会消失，并且下一次打开这个软件后，每次在判断当前是否业力衰减和每日必做扣分之前，先更新这些完成事件为已完成。」
>
> 追加纠正 1：「你要保证如果 APP 开着，然后桌面点击完成了，APP 也要能加分。这是一个易错的地方。」
>
> 追加纠正 2：「不对，应该是加分+vis=1，如果跨阶就打开 APP，否则不打开。」

**目标形态**：华为 Mate50（非 HarmonyOS NEXT，可运行标准 Android APK）桌面添加一个 **2×2 标准桌面组件（AppWidget）**，显示「每日必做」中今日尚未完成的条目；每行左侧一个圆圈；点圆圈即视为完成，该行消失，并完成加分与历史记录。

## 二、决策表（用户逐条确认）

| 项 | 决策 |
|---|---|
| 组件类型 | **集合组件（ListView + RemoteViewsService + RemoteViewsFactory）**，支持真滚动 |
| 尺寸 | 2×2（`targetCellWidth/Height = 2`，`minWidth/minHeight = 110dp`） |
| 显示内容 | 仅 `vis == 0`（未完成）的 `dailyMustDoDeeds`，每行「○ + 事件名」 |
| 全部完成时 | 显示占位文案（ListView 的 empty view） |
| 点圆圈副作用 | **标记完成（vis=1）+ 按善业默认分加分 + 写一条历史记录** |
| 加分来源 | `goodDeedPresets` 中同名下标对应的 `goodDeedDefaultScores`；找不到时兜底 `+1` |
| 写库时机 | **点击即刻写库**（组件广播接收器内直接写 Room），并立即刷新组件 |
| 是否打开 App | **默认不打开**；**仅当本次加分跨入更高正阶位时**才打开 App 弹被动自证窗 |
| 冷启动补弹自证 | 组件把「加分前/后阶位」随 Intent 带入，App 直接置入询问窗（不再依赖 `checkProof` 的基线比对） |
| 误点撤销 | **不可撤销**，点掉即视为已完成 |
| 滚动 | 采用集合组件 ListView，可垂直滚动（官方仅集合组件支持滚动） |
| 主题 | 沿用 App 深色 + 金色调 |
| 版本号 | **保持 4.3**，提交前缀 `v4.3-改N` |
| 数据库 | **不升级、不加列、不改表**（复用 `dailyMustDoDeeds.vis`） |

## 三、交互链路

```
桌面点圆圈
  → fill-in intent（携带 deed 名称）+ 模板 PendingIntent（getBroadcast, ACTION_COMPLETE_DEED）
  → DailyMustDoWidgetProvider.onReceive
      goAsync + 协程（IO）：repository.completeDailyMustDoFromWidget(deedName)
          ├ 幂等校验：非每日必做 / vis != 0 → 直接返回 null
          ├ markDeedDone(name)                  // vis → 1
          ├ addHistoryEntry(默认分, name, "record")   // 加分 + 历史
          └ 用 ProofEngine 比较加分前/后阶位 → 跨阶则返回 (oldLevel, newLevel)
      refreshAll(context)                       // 该行立即从组件消失
      仅当跨阶：startActivity(MainActivity, NEW_TASK, 携带 EXTRA_PROOF_FROM/TO)
          → MainActivity.handleWidgetProofIntent → AppContainer.requestWidgetProof
          → MainScreen 消费 → viewModel.showPendingPassiveProof(from, to) → 弹询问窗
```

**为什么自证要特殊处理**：自证窗必须由 App UI 呈现。App 进程未运行时，`checkProof` 的首个快照会把「已加分的总分」当成基线，从而漏判这次跨阶，所以由组件把阶位差直接带进去，绕开基线问题。

## 四、易错点（用户明确指出的两条）

| 风险 | 处理 |
|---|---|
| App 已开着时点击组件，加分丢失 | 组件**不经 App 写库**，而是自己直接写 Room；App 开着时 Room Flow 天然会刷新界面。跨阶时 `startActivity` + `singleTask` 会把已有实例提到前台并回调 `onNewIntent`，与 `onCreate` **共用同一处理函数**，不会丢 |
| App 进程未运行时跨阶，`checkProof` 首个快照会漏判 | 跨阶信息（oldLevel/newLevel）由组件在写库时算好，随 Intent 带进 App，`showPendingPassiveProof` 直接置入询问窗 |
| App 本来就活着 → `checkProof` 也会置入同一个询问窗 | `showPendingPassiveProof` 用 `_pendingPassiveProof.value == null` 兜底，保证只弹一次 |
| Activity 重建（旋屏/被回收恢复）重复消费 Intent | 处理完立即 `removeExtra` + `setIntent(Intent())` |
| 连点两次同一行 | 组件与 Repository 双重幂等：只有 `deed.vis == 0` 才加分，第二次点击直接返回 |
| 并发写 Room 互相覆盖 | 顺序执行（先 `markDeedDone` 再 `addHistoryEntry`，与 App 内 `onConfirm` 完全一致），且两者都是原子列更新 |

## 五、实现要点

### 1. 组件 Provider（`ui/widget/DailyMustDoWidgetProvider.kt`）

- `buildRemoteViews`：`setRemoteAdapter(R.id.widget_list, serviceIntent)` + `setEmptyView` + `setPendingIntentTemplate`。
- 模板 PendingIntent 用 **`getBroadcast`**（不再 `getActivity`），目标为 Provider 自身，action = `ACTION_COMPLETE_DEED`；`FLAG_UPDATE_CURRENT` + `FLAG_MUTABLE`（API 31+，fill-in intent 必需）。
- `onReceive`：`goAsync()` + `CoroutineScope(SupervisorJob() + Dispatchers.Main)` → `withContext(Dispatchers.IO)` 写库 → `refreshAll` → 跨阶才 `startActivity`。
- `refreshAll(context)`：静态入口，`notifyAppWidgetViewDataChanged`；无组件实例时直接返回。

### 2. 组件数据服务（`ui/widget/DailyMustDoWidgetService.kt`）

- `RemoteViewsFactory.onDataSetChanged` 用 `runBlocking` 取一次 Room 快照，过滤 `vis == 0`。
- 行布局 `widget_daily_must_do_item`：「○」用 TextView 呈现（RemoteViews 不支持自绘）；圆圈挂 `setOnClickFillInIntent` 携带 `EXTRA_DEED_NAME`。

### 3. 资源与 Manifest

- `res/xml/daily_must_do_widget_info.xml`（2×2、`updatePeriodMillis=0`）、`res/layout/widget_daily_must_do.xml`、`res/layout/widget_daily_must_do_item.xml`、`res/drawable/widget_bg.xml`、`strings.xml` 三条文案。
- Manifest：注册 `receiver`（`exported="false"` + `APPWIDGET_UPDATE` intent-filter + meta-data）与 `service`（`permission=BIND_REMOTEVIEWS`）；`MainActivity` 加 `launchMode="singleTask"`。

### 4. 数据层（`data/repository/KarmaRepository.kt`）

```kotlin
suspend fun completeDailyMustDoFromWidget(deedName: String): Pair<Int, Int>? {
    val settings = settingsDao.getSettingsOnce() ?: return null
    val deed = settings.dailyMustDoDeeds.find { it.name == deedName } ?: return null
    if (deed.vis != 0) return null                       // 幂等
    val score = settings.goodDeedDefaultScores
        .getOrElse(settings.goodDeedPresets.indexOf(deedName)) { 1f }   // 兜底 +1
    val oldLevel = ProofEngine.rankLevelOf(settings.totalScore, settings)
    markDeedDone(deedName)
    addHistoryEntry(score, deedName, "record")
    val newLevel = ProofEngine.rankLevelOf(settings.totalScore + score, settings)
    return if (settings.proofEnabled && newLevel >= 1 && newLevel > oldLevel) oldLevel to newLevel else null
}
```

### 5. 仅跨阶才走 App 的那一段

- `MainActivity`：`handleWidgetProofIntent(intent)`（`onCreate` 与 `onNewIntent` 共用），解析 `EXTRA_PROOF_FROM/TO` → `AppContainer.requestWidgetProof`；收到请求且当前不在首页时先导航回 Main。
- `AppContainer`：`WidgetProofRequest(oldLevel, newLevel, nonce)` + `StateFlow` + `requestWidgetProof` / `consumeWidgetProofRequest`。放在容器而非 ViewModel，因为 ViewModel 是**导航级**的：用户停在设置页时 `MainScreen` 未组合，请求需先暂存。
- `MainViewModel.showPendingPassiveProof(old, new)`：`null` 兜底置入。
- `MainScreen`：`LaunchedEffect` 消费请求后按 nonce 清空。

### 6. 组件刷新时机

在 **`MainActivity`** 层观察 `repository.settings`，以 `settings.dailyMustDoDeeds` 为 key：

```kotlin
val settings by appContainer.repository.settings.collectAsState(initial = null)
LaunchedEffect(settings?.dailyMustDoDeeds) {
    DailyMustDoWidgetProvider.refreshAll(this@MainActivity)
}
```

一处覆盖：① 组件点击写库（组件内自己也刷）② App 内打分与计时结算 ③ `applyDecay` 跨天重置 vis ④ 设置页改「每日必做」配置保存。
放在 Activity 层而非 `MainScreen`：用户停在设置等子页时 `MainScreen` 未组合，③④ 仍需刷新。

## 八、验证清单

1. 每步 `:app:compileDebugKotlin` 通过；最后 `:app:assembleDebug` 通过（需在有网络的环境/Android Studio 执行）。
2. 桌面能添加 2×2 组件；组件只列出未完成的每日必做，每行前有圆圈；条目多于一屏可上下滚动。
3. **不跨阶时点圆圈**：分数增加、历史出现该记录、组件该行消失，**App 完全不出现**（这是本次纠正的重点）。
4. **跨阶时点圆圈**：加分 + 该行消失，并且**自动打开 App 弹出被动自证询问窗**。
5. **App 已开着**（前台或后台）点圆圈：加分不丢；跨阶时 App 被提到前台并弹窗，不跨阶时保持后台不动。
6. 连点两次同一条 → 只加一次分（幂等）。
7. 完成全部条目 → 组件显示占位文案。
8. 跨天（或改系统时间越过衰减时刻）后组件重新显示全部条目（`vis` 被重置）。
9. 未完成项多于一屏时，组件内可上下滚动。

## 九、风险与备注

- 本机 Gradle 发行包无法下载，**无法在本机编译**，需在 Android Studio 或有网络的环境验证。
- RemoteViews 不支持自绘，圆圈用文字 `○` 呈现，视觉上比 Compose 版略朴素。
- 每日必做与善业预设是同步增删改的，正常都能查到默认分；`indexOf` 找不到时兜底 `+1`。
- **残留并发风险（既有，本次未改）**：组件在冷启动瞬间写库时，`KarmaApplication.onCreate` 的启动补扣 `applyDecay` 可能并发执行，理论上 `markDeedDone` 的「读 settings→改 vis→写」会覆盖掉 `applyDecay` 的 vis 重置，导致当天个别条目被少扣一次分（**偏宽松，不会多扣**，次日重置自愈）。该竞态在 App 内 `onConfirm` 与 2 秒轮询之间本来就存在，本次未引入新的类别；如需彻底消除，需在 Repository 引入 Mutex 串行化所有 settings 读改写。
- **既有行为（本次不改）**：`applyDecay` 一次补扣多天时，使用的是同一份 `vis` 快照，即一次「已做」会让补扣的每一天都跳过。
- 衰减判定时刻（默认 23:00）过后，`vis` 会被重置为 0，组件会重新出现全部条目（代表新一天的周期），这是预期行为，非重复。
