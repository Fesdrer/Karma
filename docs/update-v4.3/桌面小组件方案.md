# Karma 每日必做桌面小组件方案

> 本文档方案已获用户批准并实施完毕（提交 `v4.3-改14` ~ `v4.3-改19`）。
> 版本沿用 v4.3（v4.3 的改1~改13 为原有内容）。

---

## 一、需求

> 用户原话：
> 「我的手机是华为 mate50，不是满血鸿蒙系统，因此能使用这个软件。现在我要让手机桌面上多出一个小组件（服务卡片），2*2 大小，里面显示没有完成的每日必做，每一行前面会有一个圆圈，如果我点击了圆圈，这一行事件就会消失，并且下一次打开这个软件后，每次在判断当前是否业力衰减和每日必做扣分之前，先更新这些完成事件为已完成。」
>
> 追加要求：「你要保证如果 APP 开着，然后桌面点击完成了，APP 也要能加分。这是一个易错的地方。」

**目标形态**：华为 Mate50（非 HarmonyOS NEXT，可运行标准 Android APK）桌面添加一个 **2×2 标准桌面组件（AppWidget）**，显示「每日必做」中今日尚未完成的条目；每行左侧一个圆圈；点圆圈即视为完成，该行消失，并完成加分与历史记录。

## 二、决策表（用户逐条确认）

| 项 | 决策 |
|---|---|
| 组件类型 | **集合组件（ListView + RemoteViewsService + RemoteViewsFactory）**，支持真滚动 |
| 尺寸 | 2×2（`targetCellWidth/Height = 2`，`minWidth/minHeight = 110dp`） |
| 显示内容 | 仅 `vis == 0`（未完成）的 `dailyMustDoDeeds`，每行「○ + 事件名」 |
| 全部完成时 | 显示占位文案（ListView 的 empty view），如「今日必做已全部完成」 |
| 点圆圈副作用 | **标记完成 + 按善业默认分加分 + 写一条历史记录**（等同于在 App 内手动给该善业打分） |
| 加分来源 | `goodDeedPresets` 中同名下标对应的 `goodDeedDefaultScores`；找不到时兜底 `+1` |
| 完成状态写库时机 | 点击即写（经打开 App 的链路，App 内协程立即写 Room），并刷新组件 |
| 自证 | 由 **App 内既有 `checkProof` 逻辑**在「总分增加」时正常弹被动自证窗 |
| 冷启动补弹自证 | 组件点击会**自动打开/唤起 App**，App 内正常判定 → 冷启动也能弹 |
| 误点撤销 | **不可撤销**，点掉即视为已完成 |
| 滚动 | 采用集合组件 ListView，可垂直滚动（官方仅集合组件支持滚动） |
| 主题 | 沿用 App 深色 + 金色调（与主界面一致） |
| 版本号 | **保持 4.3**，提交前缀 `v4.3-改N` |

## 三、交互链路

```
桌面点圆圈
  → PendingIntent.getActivity(MainActivity, action=ACTION_WIDGET_COMPLETE_DEED, extra=deedName)
  → 拉起 / 唤起 MainActivity（singleTask）
  → MainActivity 把 deedName 交给 MainViewModel
  → ViewModel 在「自证基线就绪后」出队执行：
        ① 若 deed.vis == 0 → repository.markDeedDone(name)
        ② repository.addHistoryEntry(默认分, name, "record")
  → settings Flow 发射 → checkProof 判定「总分增加且跨入更高正阶位」→ 弹被动自证
  → 刷新桌面组件（该行消失）
```

**为什么用「打开 App」而不是组件直接写库**：自证窗需要 App 的 UI 与 `_lastTotal/_lastLevel` 内存状态，组件进程（Receiver 里）无法弹出。走 Activity 后，冷启动与 App 已开两种情况行为完全一致，也天然满足「扣分判定前先更新完成状态」——写库发生在打开 App 的瞬间，而 `applyDecay` 在其后。

## 四、易错点：App 已开着时点组件也必须加分

这是用户明确指出的风险点，逐项保证如下：

| 风险 | 处理 |
|---|---|
| App 已开着时 `startActivity` 不新建 Activity，只回调 `onNewIntent`；只在 `onCreate` 里处理 extra 会丢点击 | `MainActivity` 的 `launchMode` 改为 **singleTask**；**`onCreate` 与 `onNewIntent` 调用同一个处理函数** |
| Activity 被回收而被唤起重建时 extra 被重复消费（旋屏/重建） | 取到 deedName 后立刻 `setIntent(Intent())` 清空 extra |
| 快速连点导致重复加分 | ViewModel 内**只有 `deed.vis == 0` 才加分**（幂等）；`vis == 1` 直接忽略 |
| 加分发生在自证基线建立之前 → `checkProof` 首次发射只记基线，跨阶检测不到 | **入队 + 延迟写库**：deedName 先进队列；只有在 `repository.settings` 首次发射并建立 `_proofBaselineReady` 之后才出队写库。写库必然晚于基线，`checkProof` 下一次发射就能看到「总分增加」→ 必定判定跨阶 |
| 并发写 Room 互相覆盖（`markDeedDone` 与 `addHistoryEntry` 都是「读 settings→改→写」） | 沿用既有做法：在**同一个协程内顺序执行** ①→②，不并行（App 内 `onConfirm` 已是此写法，组件链路复用同一顺序） |

> 说明：不采用「组件 Receiver 直接写 Room」的方案，正是因为它绕过了自证判定且引入了与 2 秒 `applyDecay` 轮询的并发写风险。

## 五、实现要点

### 1. 组件 Provider

**新增 `ui/widget/DailyMustDoWidgetProvider.kt`**（`AppWidgetProvider`）：
- `onUpdate`：构造 `RemoteViews(R.layout.widget_daily_must_do)`，设置标题、`setRemoteAdapter(R.id.widget_list, intent)`、`setEmptyView(R.id.widget_list, R.id.widget_empty)`、`setPendingIntentTemplate(R.id.widget_list, 模板)`，再 `updateAppWidget`。
- 提供统一的静态刷新入口（供 App 内调用）：
  ```kotlin
  fun refreshAll(context: Context) {
      val mgr = AppWidgetManager.getInstance(context)
      val ids = mgr.getAppWidgetIds(ComponentName(context, DailyMustDoWidgetProvider::class.java))
      if (ids.isEmpty()) return
      mgr.notifyAppWidgetViewDataChanged(ids, R.id.widget_list)
  }
  ```
- **不写数据库**：`onReceive` 只响应 `onUpdate`，点击一律走 Activity。

**新增 `ui/widget/DailyMustDoWidgetService.kt`**（`RemoteViewsService` + `RemoteViewsFactory`）：
- Factory 读 `(applicationContext as KarmaApplication).container.repository.settings`（用 `runBlocking` 取一次快照，或缓存最近一次值）。
- `getViewAt`：行布局 `widget_daily_must_do_item`，「○」用 TextView 显示 `○`（RemoteViews 不支持自绘 Canvas）；文字为事件名。
- 每行对圆圈/整行 `setOnClickFillInIntent(R.id.widget_item_circle, fillInIntent)`，`fillInIntent` 携带 `EXTRA_DEED_NAME`。
- 只返回 `vis == 0` 的条目，其余不返回。

**新增资源**：
- `res/xml/daily_must_do_widget_info.xml`：
  ```xml
  <appwidget-provider
      android:minWidth="110dp" android:minHeight="110dp"
      android:targetCellWidth="2" android:targetCellHeight="2"
      android:updatePeriodMillis="0"
      android:resizeMode="horizontal|vertical"
      android:widgetCategory="home_screen"
      android:initialLayout="@layout/widget_daily_must_do" />
  ```
- `res/layout/widget_daily_must_do.xml`：标题 + `ListView`（id `widget_list`）+ 空态 `TextView`（id `widget_empty`）。
- `res/layout/widget_daily_must_do_item.xml`：`○` 圆圈 + 事件名。

### 2. Manifest

```xml
<receiver android:name=".ui.widget.DailyMustDoWidgetProvider" android:exported="false">
    <intent-filter>
        <action android:name="android.appwidget.action.APPWIDGET_UPDATE" />
    </intent-filter>
    <meta-data android:name="android.appwidget.provider"
        android:resource="@xml/daily_must_do_widget_info" />
</receiver>

<service android:name=".ui.widget.DailyMustDoWidgetService"
    android:permission="android.permission.BIND_REMOTEVIEWS"
    android:exported="false" />
```

`MainActivity` 增加 `android:launchMode="singleTask"`。

### 3. MainActivity

- `launchMode` 改为 `singleTask`（Manifest）；`onCreate` 与 `onNewIntent` 调用同一个私有函数；
- `handleWidgetDeedIntent(intent)`：取 `EXTRA_DEED_NAME` → 非空则 `setIntent(Intent())` 清 extra 后调 `container.requestWidgetDeedCompletion(name)`，防重复消费。

### 4. 请求中转与 MainViewModel

**`di/AppContainer.kt`**：新增 `WidgetDeedRequest(name, nonce)` 与 `widgetDeedRequest: StateFlow`、`requestWidgetDeedCompletion(name)`、`consumeWidgetDeedRequest(nonce)`。
放在容器而非 ViewModel，是因为 ViewModel 是**导航级**的：用户停在设置页时 `MainScreen` 未组合、ViewModel 不在场，请求需先暂存，并由 `MainActivity` 先导航回首页再处理。

**`ui/main/MainScreen.kt`**：观察 `appContainer.widgetDeedRequest`，`LaunchedEffect` 内调 `viewModel.completeDailyMustDoFromWidget(request.name)` 后 `consumeWidgetDeedRequest(request.nonce)`。

**`ui/main/MainViewModel.kt`**：
- 新增 `completeDailyMustDoFromWidget(deedName: String)`：deedName **入队**，随即尝试出队。
- 在 `repository.settings.collect { s -> checkProof(s); drainWidgetDeedQueue() }` 中，**`checkProof` 之后**才允许出队——保证基线已建立后才写库。
- `drainWidgetDeedQueue()`（`_proofBaselineReady` 门槛 + 防重入标志 + 单协程顺序执行）：
  ```kotlin
  val settings = repository.settings.first()
  val deed = settings.dailyMustDoDeeds.find { it.name == deedName }
  if (deed == null || deed.vis != 0) continue          // 幂等：非必做项/已完成直接忽略
  val index = settings.goodDeedPresets.indexOf(deedName)
  val score = settings.goodDeedDefaultScores.getOrElse(index) { 1f }   // 找不到兜底 +1
  repository.markDeedDone(deedName)
  repository.addHistoryEntry(score, deedName, "record")
  ```
  ViewModel 不持有 Context，组件刷新不在此处做（见下节）。

### 5. 组件刷新时机（实现方式）

在 **`MainActivity`** 层观察 `repository.settings`，以 `settings.dailyMustDoDeeds` 为 key 的 `LaunchedEffect` 调用 `DailyMustDoWidgetProvider.refreshAll(...)`：

```kotlin
val settings by appContainer.repository.settings.collectAsState(initial = null)
LaunchedEffect(settings?.dailyMustDoDeeds) {
    DailyMustDoWidgetProvider.refreshAll(this@MainActivity)
}
```

一处即可覆盖全部四条路径：① 组件点击写库、② App 内打分与计时结算（改 vis）、③ `applyDecay` 跨天重置 vis、④ 设置页改「每日必做」配置保存（`resetDailyMustDoVis`）。
放在 **Activity 层而非 `MainScreen`**：用户停在设置/誓约等子页时 `MainScreen` 未被组合，上述 ③④ 仍需要刷新组件。组件未添加到桌面时 `refreshAll` 内部取到空 id 数组直接返回，无额外开销。

## 八、验证清单

1. 每步 `:app:compileDebugKotlin` 通过；最后 `:app:assembleDebug` 通过（**需在有网络的环境/Android Studio 执行**）。
2. 桌面能添加 2×2 组件；组件只列出未完成的每日必做，每行前有圆圈。
3. **App 未运行**时点圆圈 → App 自动打开 → 总分增加、历史出现该记录 → 回到桌面该行消失。
4. **App 已开着**（前台或后台）点圆圈 → 不新建界面，直接加分、该行消失（验证 `onNewIntent` 链路，本次重点）。
5. 加分跨入更高正阶位时**弹出被动自证窗**；App 冷启动场景同样能弹（验证队列 + 基线时序）。
6. 连点两次同一条 → 只加一次分（幂等）。
7. 完成全部条目 → 组件显示占位文案。
8. 跨天（或改系统时间越过衰减时刻）后组件重新显示全部条目（`vis` 被重置）。
9. 未完成项多于一屏时，组件内可上下滚动。

## 九、风险与备注

- 本机 Gradle 发行包无法下载（`services.gradle.org` 连接超时），**无法在本机编译**，需在 Android Studio 或有网络的环境验证。
- 组件点击会**打开 App**（为满足自证正常弹出）。这是既定取舍；若后续觉得打扰，可改为「组件只标记完成、不打开 App」，但那样跨阶自证需要新增「待判定」持久化字段才能补弹。
- RemoteViews 不支持自绘，圆圈用文字 `○` 呈现，视觉上比 Compose 版略朴素。
- 每日必做与善业预设是同步增删改的，正常都能查到默认分；`indexOf` 找不到时兜底 `+1`。
- **既有行为（本次不改）**：`applyDecay` 一次补扣多天时，使用的是同一份 `vis` 快照，即一次「已做」会让补扣的每一天都跳过。
- 衰减判定时刻（默认 23:00）过后，`vis` 会被重置为 0，组件会重新出现全部条目（代表新一天的周期），这是预期行为，非重复。
