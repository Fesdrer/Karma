# Karma v4.4 更新计划

## 上下文

本次更新从 v4.3 出发。它起源于一次**数据恢复**：用户发现历史记录起点从 1 月变成了 6 月，怀疑记录被删除。排查后确认是真的——历史记录有 2000 条上限，超出时静默删最旧的。恢复过程中又顺带发现并修复了另外三处 bug，最后追加一处分数显示问题。

**版本**：`build.gradle.kts` versionName "4.3" → "4.4"，versionCode 25 → 26。
**数据库**：无变化（Room version 保持 27，未加列、未改表）。

本次含 **5 项改动**：

1. **历史记录取消 2000 条上限**（★ 根因修复，本次起因）
2. **时间/日期滚轮有时不自动居中**（★ 根因修复）
3. **桌面组件跨天时 `vis=1` 被衰减重置**（★ 根因修复）
4. **自证窗口点外部即可零成本逃避**（★ 根因修复）
5. **事件默认分被刻度上限夹掉**（★ 根因修复，收尾追加）

## 〇、数据恢复（改动 1 的由来）

### 现象

用户原话：

> 原本这个记录是从 1 月分开始的，但是我今天翻了一下，竟然从 6 月份开始了！之前的记录都消失了！

App 当时显示 2000 条，起点 `2026-06-06`。

### 根因

`KarmaRepository.addHistoryEntry()` 每次写入后 `getCount()`，超出 `MAX_HISTORY = 2000` 就调用 `trimOldest(excess)` 删除最旧记录：

- **不提示**用户
- **不备份**
- **界面不可见**（历史页只显示已有内容，看不到"被删了多少"）

于是历史起点被一路推向 6 月。实测被吃掉 **117 条**（`2026-02-07 23:55:30` → `2026-06-04 00:02:58`）。

### 恢复过程

在本机找到 **14 份**历史数据副本（git blob + Downloads + Desktop），取并集：

| 阶段 | 条数 | 说明 |
|---|---|---|
| 1. 全部记录并集 | 4397 | 含重复与测试数据 |
| 2. 排除测试文件 | 3838 | 剔除合成 fixture |
| 3. 用户本人记录 | 2089 | 起点 `2026-02-07` |
| 4. 补回丢掉的 | 117 | App 里缺失的那段 |

**识别出两份合成测试数据**（非用户真实记录，已排除）：

- `docs/test_data.json` — 2025 年，通用预设词汇，无 `id` 字段
- `karma_test_data.json` — 2026-01 → 06，同样无 `id` 字段

另发现两个特征可佐证：一段**恒定步长**记录（间隔恒为 `11777.731` 秒 ≈ 3h16m17.731s），以及 `2026-06-12 10:43` 一次性导入 **962 行**。

> 恢复产物放在 `_recover/`（已加入 `.gitignore`，不入版本控制）。用户可见的交付物是桌面上的合并 JSON，通过「历史页 → 导出/导入 → 导入」补回。

## 一、历史记录取消 2000 条上限

### 需求（用户确认）

> 把上限改成无穷。

### 决策表

| 项 | 决策 |
|---|---|
| 上限值 | `Int.MAX_VALUE`（2147483647） |
| 是否保留 `trimOldest` | 保留函数，但删除分支不再可能触发 |
| 是否加"清理历史"按钮 | 不加（用户未要求，且改动应最小） |

### 实现要点

**`KarmaRepository.kt`**：

```kotlin
// 原：private const val MAX_HISTORY = 2000
private const val MAX_HISTORY = Int.MAX_VALUE
```

`addHistoryEntry` 里的判定为 `excess = count - MAX_HISTORY`，`if (excess > 0) trimOldest(excess)`。
改成 `Int.MAX_VALUE` 后 **`count - MAX_HISTORY` 恒为负**，`excess > 0` 永不成立，删除分支死掉（真要触发需 21 亿条记录）。

## 二、时间/日期滚轮有时不自动居中

### 现状问题（根因）

`ScrollPicker.kt` 的吸附逻辑只在**一次滚动结束**的那一刻执行：

```kotlin
snapshotFlow { listState.isScrollInProgress }
    .collect { if (!it) snapToCenter() }
```

两个漏洞：

1. **布局未就绪就 return，之后再不补做**。`snapToCenter()` 里依赖 `listState.layoutInfo.visibleItemsInfo`；弹窗刚出现、首帧还没测量完时该列表为空，函数直接返回。而 `snapshotFlow` **只在值变化时发射**——这一次吸附被跳过后，除非用户再滚一次，否则永远不会补。
2. **软键盘弹出/收起改变视口高度时没有滚动事件**。此时 `viewportEndOffset` 变了，但 `isScrollInProgress` 没变，snapshotFlow 不发射，滚轮停在偏移位置。

另有两处独立错误：

3. **点击某一项不居中它**。原代码点击后滚到 `index`，而 `index` 是该项停在**顶部**的位置；5 格可视区真正居中的是 `index + 2`。
4. **布局未就绪时把"第一项"当成选中值发射**。`centerItemIndex` 原兜底为 `0`，于是年份滚轮在弹窗刚出现时被莫名改成列表第一项（2024）。另外点击取值用 `value % baseSize`，当 range 不以 0 开头（如 `2024..2100`）时取模会算出一个完全无关的项。

### 决策表

| 项 | 决策 |
|---|---|
| 重试策略 | 抽出 `snapPickerToCenter()` 返回布尔值，外层最多重试 20 次 × 16ms ≈ 300ms |
| 额外触发源 | 把 `viewportEndOffset` 纳入 `snapshotFlow` 监听 |
| 点击对齐 | 滚到 `index - visibleItems / 2`（`visibleItems = 5`） |
| 未就绪时 | `centerItemIndex` 返回 `-1`，且不发射 |

### 实现要点

**`ScrollPicker.kt`**：

- 新增 `private const val PICKER_VISIBLE_ITEMS = 5`；
- 新增 `private suspend fun snapPickerToCenter(listState, visibleItems, totalSize, animate): Boolean`——**布局未就绪时返回 `false`**，让调用方知道"没做成，要重试"；
- `LaunchedEffect(Unit)` 改为监听 `listState.isScrollInProgress to listState.layoutInfo.viewportEndOffset` 这一对；停止滚动后 `delay(60)` 给布局一点时间，再进入最多 20 次的 `delay(16)` 重试循环，成功即 `break`；
- `centerItemIndex` 未就绪时返回 `-1`；`LaunchedEffect(centerItemIndex)` 遇到 `idx < 0` 直接跳过；
- 点击处理改为滚到 `(index - PICKER_VISIBLE_ITEMS / 2).coerceIn(0, totalSize - 1)`，并调用 `onSelected(baseItems[index % baseSize])`（原来是 `value % baseSize`）。

> 收敛性说明：重试循环在 `diff < 4f`（已经居中）时返回 `true` 并 break。`animateScrollToItem` 引起的 `isScrollInProgress` 变化会再次触发 snapshotFlow，但那时 diff 已经小于 4f，不会再滚动，因此不会无限循环。

## 三、桌面组件跨天时 `vis=1` 被衰减重置

### 现象

用户问：

> 使用桌面组件按下按钮后，如果跨越阶位，会不会忘记把 vis 标记为 1？

排查后确认：**跨阶位无关**，但确实存在一个 `vis` 被覆盖的路径。

### 现状问题（根因）

`applyDecay()` 的 step 3 会把**所有** deed 的 `vis` 重置为 `0`（表示进入新的一天）。

原 `completeDailyMustDoFromWidgetLocked()` 的顺序是：

```
① markDeedDone(deedName)   // vis → 1
② addHistoryEntry(...)     // 加分
```

如果**衰减日恰好在这一刻之后才结算**，step 3 会把刚写好的 `vis=1` 一起清掉。用户看到：

> 点了圆圈、分数也加了，但那一行又回到组件里，第二天还按未完成再扣一次。

**触发条件**：App 进程在后台存活，但 ViewModel 的 2 秒衰减轮询被系统冻结；用户在衰减时刻**之后**才点组件——写库跑在轮询恢复之前。

### 决策表

| 项 | 决策 |
|---|---|
| 修复方式 | 在函数开头先 `applyDecayLocked()` 补结算，再写 `vis=1` |
| 死锁风险 | 无——`applyDecayLocked` 是不加锁的内部实现，外层 `applyDecay` 才加锁 |
| 幂等性 | `lastDecayDate` 已推进后，轮询里的 `applyDecay` 直接返回 0 |
| 阶位基准 | 补结算可能改总分，必须**重新读快照**再算"加分前阶位" |

### 实现要点

**`KarmaRepository.kt` · `completeDailyMustDoFromWidgetLocked()`**：

```kotlin
// ★ 先结算可能已经跨过的衰减日
applyDecayLocked()

// 补结算可能改了总分，重新读快照再算「加分前阶位」
val settings = settingsDao.getSettingsOnce() ?: return null
val deed = settings.dailyMustDoDeeds.find { it.name == deedName } ?: return null
if (deed.vis != 0) return null
val oldLevel = ProofEngine.rankLevelOf(settings.totalScore, settings)

markDeedDone(deedName)          // ① vis → 1
addHistoryEntry(score, deedName, "record")   // ② 加分
```

本函数与 `applyDecay` **共用同一把 `settingsWriteMutex`**，所以：

- 若本函数先拿锁 → 补完结算，`lastDecayDate` 推进 → 轮询里的 `applyDecay` 幂等返回；
- 若轮询先拿锁 → 本函数拿锁时衰减已结算完，`applyDecayLocked()` 同样幂等返回。

**两种顺序下 `vis=1` 都不会再被覆盖。**

## 四、自证窗口点外部即可零成本逃避

### 现状问题（根因）

`PassiveProofPromptDialog` 的 `onDismissRequest` 挂的是调用方传进来的 `onDismiss`，而那个值是 `clearProofSetup()`——**点弹窗旁边或按返回键就把整个询问窗清掉**。

这跟该函数自己的注释写的「点弹窗外忽略」**正好相反**，后果是：用户加了分跨阶、被被动窗拦住，只要点一下旁边就能白退，等于**零成本逃避自证**。

同一条链上还有第二个口子：即使询问窗堵住了，用户选「设置自证」进入设置窗后，**再点设置窗外部**依然能白退。

### 决策表

| 项 | 决策 |
|---|---|
| 询问窗 | `onDismissRequest = { }`，并删除 `onDismiss` 参数（不再有"清掉"这条路） |
| 设置窗 | 同样 `onDismissRequest = { }`，禁止点外部/返回键关闭 |
| 被动模式取消 | 按钮文案改「逃避自证（扣分退回）」，按逃避扣分 |
| 主动模式取消 | 文案仍为「取消」，**不扣分**（用户自己点进来的，什么都没发生） |
| 逃避代价 | 两条路径统一走 `escapeProof()`，保证一致 |

### 实现要点

**`ProofDialogs.kt`**：
- `PassiveProofPromptDialog`：删除 `onDismiss` 参数，`onDismissRequest = { }`；
- `ProofSetupDialog`：`onDismissRequest = { }`；`dismissButton` 按 `setup.mode == ProofMode.PASSIVE` 分支，被动模式文案为「逃避自证（扣分退回）」。

**`MainViewModel.kt`**：
- 新增 `private fun escapeProof(newLevel: Int)`——把分数扣到该阶位阈值 −1，写历史 `"逃避自证"`；
- `onPassiveProofEscape()` 改为委托 `escapeProof(p.newLevel)`；
- 新增 `fun cancelProofSetup()`：清空 `_proofSetup` / `_pendingPassiveProof`；**仅当被动模式**时调 `escapeProof(setup.target)`；
- 删除已无调用方的 `clearProofSetup()`。

**`MainScreen.kt`**：
- `PassiveProofPromptDialog(...)` 不再传 `onDismiss`；
- `ProofSetupDialog(onDismiss = { viewModel.cancelProofSetup() })`。

> 附带说明：`ProofSetupDialog` 被动模式的 `target` 是"已达阶位" `p.newLevel`，`escapeProof` 用它的阈值 −1 作为扣分目标，与询问窗的逃避结果一致。

## 五、事件默认分被刻度上限夹掉

### 现象（用户原话）

> 就是比如事件分数很大，打过了左边的分数上限，那分数就不会显示那个分数，而是那个上限

澄清后确认用户要的行为是：

> 就是那个选择的红色圆球在 6 的位置，但是最上面显示 10。一开始不就是这样子的吗

即：**数字要显示真实分数（10），红球停在刻度顶端（6 的位置）**。

### 现状问题（根因）

`MainViewModel.selectEvent()` 里：

```kotlin
val clamped = score.coerceIn(_currentScoreAxisRangeMin, _currentScoreAxisRangeMax)
_selectedScore.value = clamped
```

它把**「左侧刻度画到哪」当成了「分数的合法范围」**。设显示范围为默认 `-6 ~ 6` 时，一个默认分 10 的事件被静默改成 6，最上面显示的数字也跟着变成 6。

**二者本是两件事**：

| | 受不受刻度范围限制 | 说明 |
|---|---|---|
| 红球位置 | 不受（内部自适应） | `ScorePanel.scoreToAxisY` 里有 `ratio.coerceIn(-1f, 1f)`，超范围时球自动停在刻度顶端 |
| 最上面的数字 | **不受** | 直接显示 `_selectedScore`，原样填 10 就显示 10 |
| 在刻度上点击/拖动 | **受** | 这是刻度范围唯一该管的地方 |
| 历史图表纵轴 | 不受 | `HistoryChartCanvas` 用 points 的 min/max 自适应 |

所以正确做法就是**原样赋值**——球的位置由 `scoreToAxisY` 自己兜住，不需要在 ViewModel 里提前夹取。

### 实现要点

**`MainViewModel.kt`**：

```kotlin
// 修复前
val clamped = score.coerceIn(_currentScoreAxisRangeMin, _currentScoreAxisRangeMax)
_selectedScore.value = clamped
_effectiveScoreState.value = clamped

// 修复后
_selectedScore.value = score
_effectiveScoreState.value = score
```

同时删除两个因此变成**只写不读**的字段 `_currentScoreAxisRangeMin` / `_currentScoreAxisRangeMax` 及其赋值（留着会误导后来人以为分数真的受刻度限制）。

**刻度范围仍然只限制** `ScorePanel` 的 `pointerInput` 分支——即手指在刻度上点击/拖动能取到的分数。

### 数值验证（改动五）

按 `scoreToAxisY` 的公式（`mid = (max+min)/2`、`half = (max-min)/2`、`ratio = (score-mid)/half` 再 `coerceIn(-1,1)`）验算：

| 分数 | 夹取后 ratio | 结论 |
|---|---|---|
| 6 | 1.00 | 停在刻度顶 |
| 10 | 1.00 | **同样停在刻度顶**（球不动，数字显示 10） |
| -20 | -1.00 | 停在刻度底 |

`10` 与 `6` 算出同一个 ratio，证明球的位置天然被兜住，无需 ViewModel 干预。

## 七、非目标（本次明确不做）

1. **不加"清理历史"入口**——用户只要求取消上限，没要求手动清理。
2. **不改经文启动画面的显示规则**——用户确认过"退出后很快再打开不显示经文"是**正常行为**：`splashShown` 是进程级变量，Android 退出后不会立刻杀进程，系统复用老进程时该变量仍为 `true`。当前规则「每次进入应用显示一次」保持不变。
3. **不改悬浮窗权限申请方式**（`Settings.ACTION_MANAGE_OVERLAY_PERMISSION`）——属于"需要高 API 支持"的实现，非本次范围。
4. **不动 `_recover/` 里的恢复产物**——保留在本机，已加入 `.gitignore` 不入版本控制。
